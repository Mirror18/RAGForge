# 00-需求处理与最终效果

这是项目最先阅读的结果总览。它回答四个问题：为什么做、要解决什么需求、代码和工程如何处理、最后达到什么效果。任务卡的预算与依赖见 [`09-项目任务总台账.md`](./09-项目任务总台账.md)，当前状态见 [`08-项目状态卡.md`](./08-项目状态卡.md)，具体提交细节以 Git history 为准。

## 1. 项目要解决的问题

RAGForge 不是一个只返回文本的聊天 Demo，而是一个面向企业内部、多用户知识空间的可部署 RAG 工程。核心要求是：

- 用户可以把文件、网页、Git 等来源放入自己的知识空间，并知道每份内容处于什么处理状态。
- 内容经过可追溯的 revision、artifact、解析、分块、embedding、索引和发布流程后，才能参与问答。
- 每次问答都必须保留来源、chunk、evidence 和 citation provenance；不能用模型自由生成的文本冒充引用。
- 不同知识空间之间必须严格隔离；每次内容查询和变更都强制携带 `space_id`。
- 本地模型是默认路线；云端 Provider 只有在空间明确授权后才能调用，不能从本地失败静默切换到云端。
- 系统需要具备失败重试、幂等、观测、评估、安全扫描、备份恢复和后续 Linux 部署能力。

## 3. 当前已经达到的效果

### 3.1 产品闭环

当前已形成从配置、来源接入、异步摄取、候选索引、active 发布、检索、引用问答、引用预览、反馈、审计到管理视图的本地闭环。真实浏览器和本地 Ollama 验收使用公共 synthetic 内容，未把个人 Obsidian 内容或生产数据写入仓库。

### 3.2 工程闭环

- 业务 API 和应用编排集中在 `backend/server`。
- 异步来源同步与索引任务集中在 `backend/ingestion-worker`。
- OCR 和 rerank 的运行面集中在 `backend/ai-runtime`，不承担业务数据写入和第二套业务 API。
- Vue SPA 集中在 `frontend/ragforge-web`。
- `contracts/` 是公共 API/event 真源；`tests/` 是跨应用和验收测试；`fixtures/` 是可复现样本；`scripts/` 是仓库级自动化。这些目录保留是因为代码真实调用它们，不是因为空目录介绍。

### 3.3 质量和安全闭环

当前门禁已覆盖格式、Markdown 链接、架构边界、OpenAPI/Controller 双向覆盖、秘密扫描、观测资源、契约、Web、Maven、RAG 评估、SBOM/Grype 和 Compose 静态规则。安全底线仍是 `space_id` 强制隔离、结构化 provenance、云出境显式授权和 fail-closed。

## 4. 尚未完成与下一步

当前主线仍是 Phase 7 `p2-execution`：

1. `P7D-03`：准备独立、干净的 Ubuntu 24.04 WSL/VM，按部署文档从零执行初始化、摄取、active index、引用问答、反馈、审计和跨空间/云出境拒绝验收。
2. `P7D-03` 通过后，按顺序进入 P7D-04～07：观测叠加、升级/回滚、公共化清理和阶段闭环。
3. 在没有独立 Ubuntu 24.04 环境时，保持 `P7D-03` 为 `BLOCKED`，不以 Windows 共享卷或现有 Compose 卷替代部署结论。

当前没有需要新增业务功能的模糊任务；如果要开发新能力，先在 [`09-项目任务总台账.md`](./09-项目任务总台账.md) 增加明确的需求、处理方式、ownership、验收和预算，再创建 Ticket。
